1. 최종 목표 (Big Picture)
1.1 무엇을 만들고 싶은가

고정된 영상 분석 파이프라인(DeepStream식)을 대체하는

동적 DAG 기반 Stream Pipeline Framework

영상(RTSP/VMS)을 포함하되, 영상에만 한정되지 않는 범용 데이터 스트림 처리 프레임워크

1.2 핵심 특징

Node = thread/worker 개념

채널 단위, 객체 단위로 실행되는 DAG가 서로 다를 수 있음

프로세스가 떠 있는 상태에서:

DAG 자체 교체 가능

DAG에 노드(모델) 추가/삭제 가능

2. MVP 범위 정의 (명확히 축소)
2.1 MVP의 목표

RTSP → decode → detection → output 까지의 E2E 파이프라인 완주

성능 최적화보다 프레임워크 골격, 계약, 스케줄 구조 검증이 우선

2.2 MVP에서 하지 않기로 한 것

Triton Server 기반 운영/모델 관리

멀티 디바이스(AMD/Intel) 완전 지원

복잡한 동적 DAG 엔진

zero-copy 완전 최적화

3. 추론 스택 관련 논의 요약
3.1 전제

NVIDIA가 시장의 절대 다수 → NVIDIA 기준 최적화를 망치지 않는 것이 최우선

비-CUDA 디바이스(AMD/Intel)는 “수용 가능 수준의 타협”은 허용

device memory 직접 access / copy 최소화는 핵심 철학

단, 모든 디바이스에서 강제하지는 않음

3.2 각 스택에 대한 인식 (합의)
TensorRT

단일 추론기, in-process

device ptr / CUDA stream / lifetime을 개발자가 100% 통제 가능

NVIDIA에서 유일하게 진짜 zero-copy 파이프라인이 가능한 선택지

단점: 운영·모델 교체·스케줄링은 직접 구현해야 함

Triton

ORT와 TRT의 “중간”이 아님

추론 엔진이 아니라 Inference Server

모델 업로드/버전/인스턴스/스케줄링 관리가 강점

메모리 경로·실행 시점은 서버 정책에 일부 종속

MVP 범위에서는 과함

ONNX Runtime (ORT)

범용성 최고 (NVIDIA/AMD/Intel/CPU)

인터페이스 통일에는 매우 유리

그러나:

device memory를 “1급 시민”으로 다루기 어려움

I/O Binding도 copy를 완전히 통제하기는 어려움

device-resident pipeline을 하드 요구사항으로 두면 장기 메인으로는 부적합

OpenVINO

Intel 쪽에서는 가장 성숙

Remote Tensor/Remote Context로 핸들 기반 memory sharing 가능

Intel 디바이스용 adaptor 후보

ROCm

AMD 쪽은 단일 “TensorRT 같은 정답”이 없음

현실적으로 ORT ROCm EP + copy 최소화 전략이 최선
